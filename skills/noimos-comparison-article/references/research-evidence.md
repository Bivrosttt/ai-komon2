# 比較記事リサーチ基準

## ソースの優先順位

1. 公式プロダクトページ・公式ドキュメント
2. 公式料金ページ・請求仕様・usage仕様
3. 国内の独立レビュー、導入レビュー、ユーザー口コミ
4. 海外の独立レビュー、G2、Capterra、Trustpilot、Reddit等

公式情報は「機能が存在するか」「価格とusageはいくらか」に使い、口コミは「使い勝手・不満・サポート・学習コスト」の傾向に使う。口コミを公式仕様の代わりに使わない。

## サービス導線と料金ソースの分離

- サービス名、H1、結論、比較表の主リンクは、そのサービスの公式ホーム（または公式プロダクトホーム）へ向ける。
- `/pricing`、`/plans`、課金画面はサービス導線に使わず、価格セルまたは調査ソース欄で「料金」「Pricing」と明示したリンクに限定する。
- 調査台帳には `home_url` と `pricing_url` を別フィールドで保存し、DOM検証では初出リンクが `home_url` と一致することを確認する。

## 1サービスにつき最低限集める項目

| 分類 | 必須項目 |
| --- | --- |
| 公式機能 | 主用途、入力、出力、連携、対応言語・地域、代表機能 |
| 公式料金 | 無料枠、プラン名、月額/年額、請求単位、usage上限、超過課金、席数 |
| 国内口コミ | 良い点、不満、日本語品質、サポート、料金への反応 |
| 海外口コミ | 良い点、不満、安定性、学習コスト、課金への反応 |
| 判断 | 向く読者、向かない読者、第一候補になる用途、代替候補 |

## ホーム画面スクリーンショット

- 公式ホームURLをブラウザで開き、1440×900を基準にスクリーンショットを保存する。
- ファイルは記事の`home-screens/`へ置き、サービスレビューの`h3`直前に`figure.service-home-shot`として配置する。
- `figcaption`には「公式ホーム画面」「取得日」「公式URL」を含める。スクリーンショットは機能や価格の証拠ではなく、読者が画面の方向性を掴むための視覚資料として扱う。
- Cloudflare・ログイン・エラー画面は採用しない。公式Docsに掲載されたProject Editorなどのプロダクトホーム画面を使う場合は、captionに「公式Docs掲載」と書き、出典URLを台帳へ残す。
- 第三者ブログや画像検索結果の画像を公式ホーム画面として転載しない。

## 価格スナップショット

価格は取得日と通貨を必ず保存する。年払いの月換算は、年額を12で割ったことを明示する。クレジット・分数・文字数・席数などusageが異なる候補は、代表シナリオ（例：月10本、月20時間、月5席）を定義して比較する。

価格が公式ページにない、ログイン後のみ、地域で変わる場合は、記事に「公開情報では算定不能」と書く。読者を公式ページへ送り返す「確認してください」では済ませない。

## 口コミの扱い

- 取得日、媒体、URL、評価、本文の要旨を保存する。
- 単発の極端な高評価・低評価は「個別レビュー」として扱い、一般傾向にしない。
- 2つ以上の独立レビューで共通する内容は「レビューで目立つ傾向」と書く。
- 口コミの感想を価格・usage・機能の事実へ拡張しない。
- 有料レビュー、アフィリエイト、公式導入事例は独立口コミと分けてラベル付けする。

## コスパの書き方

コスパは「安い」ではなく、代表シナリオでの成果物数、usage消費、実効月額、作業削減の見込みを同じ枠で比較する。実測していない作業時間や売上を創作しない。計算できない項目は「公開情報では算定不能」とし、価格とusageの差を説明する。
