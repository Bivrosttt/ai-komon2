# Presentation Design Review

## 最重要方針

このスキルは、PowerPointのXMLや要素数を採点するチェッカーではない。レンダリングした画像をAIデザイナーが実際に見て、何が弱いかを言語化し、修正案を作り、再レンダリングして再確認するための技能である。

数値・ルール・機械的なPASS判定だけで資料を合格にしない。見た目が10〜20点に感じられる資料を「文字サイズは適正」「はみ出しなし」で通してはいけない。

## この技能を使う条件

- 既存の資料を改善するとき。
- 「AIっぽい」「テンプレ感がある」「ビジュアルが弱い」「つまらない」と言われたとき。
- 同じタイトル位置、カード、2カラム、白背景が連続しているとき。
- 数字や文章は正しいのに、経営者が最後まで読み進めないとき。
- 無料相談、営業、社内決裁など、最後の行動まで設計する資料。

## 禁止事項

- `slides_test.py`、要素数、座標、フォントサイズ、コントラスト比だけで品質を合格にしない。
- 自動スコアを先に見て、画像を見た気になるな。
- コンタクトシートだけで「全ページ確認済み」と言わない。コンタクトシートは流れを見るためだけに使い、各ページは原寸で開く。
- 作り手が見慣れた資料を自分に甘く採点しない。「問題がないか」ではなく「素人っぽい箇所はどこか」から探す。
- 1ページを見て全ページの品質を推測しない。
- 画像、アイコン、線、角丸カードを装飾として足して、主張の弱さを隠さない。

## レビューの入力

必須入力は次の3つ。

1. 対象PPTXまたはPDF。
2. 想定読者、資料の目的、読後にしてほしい行動。
3. 参考画像・参考資料がある場合は、その理由。「色を参考にする」ではなく「問題提起ページの余白と視線誘導を参考にする」と具体化する。

情報が不足していても、まず資料そのものから仮説を立てる。確認質問は、デザインの方向性を大きく変える場合だけにする。

## レビューの基本姿勢

### 「美しい」ではなく「強い」を見る

各ページについて、次の問いに答える。

- 0.5秒見たとき、最初にどこへ視線が行くか。
- 3秒見たとき、何を主張しているページに見えるか。
- タイトルを隠しても、何を伝えたいか残るか。
- 読者が次のページを見る理由があるか。
- その画像・図解・数字が無くなると、理解が落ちるか。
- 経営者が「自社にも当てはまる」と思う具体性があるか。
- そのページは、前のページの問いに答えるか、次の問いを生むか。

### 最初のレビューは厳しくする

最初のレンダリングでは、最低3つ以上の改善点を探す。「問題なし」は禁止。見つからない場合は、次の観点を変えてもう一度見る。

- 雑誌・広告のアートディレクターとして見る。
- 社長が30秒で流し読みする資料として見る。
- 初心者が初めて読む教材として見る。
- 競合の無料資料と並べたときに選ばれるかで見る。
- AIが量産したテンプレートに見える箇所を探す。

## 5段階のAI目視レビュー

### Stage 1: 目的とカスタマージャーニー

最初に、資料のデザインを評価せず、読者の感情と判断の流れを1行ずつ書く。

```text
読者: 社長・決裁権を持つ経営者
入口の悩み: AIを導入したいが、何から判断すべきか分からない
拡大する不安: 小さな実験を繰り返すだけで、現場も予算も消耗する
見せる最悪の未来: ツールだけ増え、責任者が不在のまま成果が出ない
見せる最高の未来: 小さな検証から始め、経営判断できるAI活用に変わる
提示する手段: 判断条件 → 対象業務 → 小さな検証 → 定着の順で進める
最後の行動: 無料顧問1回分で自社の優先順位と最初の検証を決める
```

この流れに対して、各ページに次の一つだけを割り当てる。

- 問題を発見する
- 問題を自分ごと化する
- 失敗のコストを想像する
- 成功した状態を想像する
- 解決策の考え方を渡す
- 自力でやる場合の最初の一歩を示す
- 自力では詰まる地点を明らかにする
- 相談する価値を提示する

「内容が正しいページ」でも、この流れに不要なら削除または統合する。

### Stage 2: デッキ全体の第一印象

全ページを小さく並べたコンタクトシートを見て、次を文章で評価する。

- 同じ構図が何ページ続くか。
- 白背景、カード、中央揃え、同じタイトル位置が多すぎないか。
- 章の切れ目が視覚的に分かるか。
- 低密度の呼吸ページと、情報を理解するページが交互にあるか。
- 表紙からCTAまで、視線が単調に流れていないか。
- 1枚だけ異質なページがないか。
- 画像、図解、チャート、引用、数字、文章の使い分けがあるか。

同じ構図が3回以上連続する場合、文字を変えるだけでは修正と認めない。ページの役割に応じて、構図そのものを変える。

### Stage 3: 各ページの原寸レビュー

レンダリングした全ページを1枚ずつ原寸で開く。各ページについて、次の記録を残す。

```text
Slide 07
一言で見えたこと:
このページの本来の仕事:
最初に視線が行った場所:
主張の強さ: 強い / 普通 / 弱い
見つけた問題:
- [Critical] 読者が最初に見る場所がタイトルではなく小さなラベルになっている
- [Major] 左右のカードが同じ強さで、どちらを選ぶべきか分からない
- [Minor] 下部の補足が本文と同じ濃さで主張を薄めている
修正案:
1. ...
2. ...
```

必ず見る項目は次の通り。

#### 文字とレイアウト

- タイトルは主張になっているか。「AI導入の進め方」のような名詞だけで終わっていないか。
- タイトル、本文、注釈の強弱が一目で分かるか。
- 日本語の折返し、孤立した一文字、カード内の上下の偏りがないか。
- 長い文章を小さくして押し込んでいないか。削る・分ける・見せ方を変える。
- 中央揃えが本当に必要か。本文と長文は原則左揃えにする。
- 余白が「余っている」のか「呼吸をつくっている」のかを区別する。

#### 構図と視線

- 重要な要素が一つだけ最大になっているか。
- すべての要素が同じサイズ・同じ濃さ・同じカードになっていないか。
- 左右の重さが釣り合っているか。釣り合わない場合は意図があるか。
- 視線の入口と出口が設計されているか。
- 図解や矢印が、読む順序を明確にしているか。単なる飾りになっていないか。
- ページ端・カード端・画像端が不自然に近くないか。

#### ビジュアルの意味

- 画像を見ただけで、ページの主張と関係があるか。
- 写真の人物の視線、余白、切り取り方が文章を助けているか。
- チャートは数字を見せるだけでなく、何を判断すべきか示しているか。
- 図解は構成要素を増やすほど理解を助けているか。箱と矢印の羅列になっていないか。
- 画像が無くても同じ意味なら、画像は削除候補。

#### AIっぽさ

- 毎ページ同じ角丸カード、同じ影、同じアクセント線を使っていないか。
- 意味のないグラデーション、光、丸、ドット、線を足していないか。
- 「それっぽい」抽象イラストで具体性の不足を隠していないか。
- タイトルの語尾や構文が機械的に繰り返されていないか。
- 余白が均一すぎて、雑誌・広告・プレゼンとしての抑揚がないか。
- どこかで見たテンプレートの部品を並べただけに見えないか。

### Stage 4: 厳しいデザインレビュー

Stage 3の記録をもとに、別人格のシニアプレゼンデザイナーとして再レビューする。作り手の意図を忖度しない。

```text
あなたは、社長向けの営業・戦略資料を作ってきたシニアプレゼンデザイナーです。
この資料を納品物として受け取ったつもりで、甘く評価しないでください。
「問題がない」と言わず、AIっぽい箇所、素人っぽい箇所、視線が止まる箇所、
意味のない装飾、同じ構図の反復、CTAまでの理由不足を具体的に挙げてください。
各指摘は「何が」「なぜ弱く」「どう直すか」の3点で書いてください。
最初の案は原則として不合格とし、修正後にもう一度全ページを見てください。
```

### Stage 5: 修正と再レビュー

1. Criticalを先に直す。主張不明、カスタマージャーニーの断絶、CTAの理由不足を優先する。
2. Majorを直す。構図の反復、主役不在、ビジュアルの意味不足、余白の偏りを直す。
3. Minorを直す。折返し、行間、微細な整列、色の濃淡を直す。
4. 修正後に全ページを再レンダリングする。
5. 変更したページだけでなく、前後のページとコンタクトシートを再確認する。
6. 2回目のレビューでも問題が残る場合、細部ではなく構成を作り直す。

## デザインDNAの抽出

参考資料がある場合は、色だけを真似ない。2〜3個の承認済み資料から次を言語化する。

- 画像と文字の位置関係
- 表紙・章扉・本文・事例・CTAの構図
- 大きな数字と小さな補足の比率
- 余白のリズム
- 固定する要素と、ページごとに変える要素
- 1ページあたりの実際の文字量
- 写真、図解、チャート、引用の使い分け

色・ロゴ・フォントが合っていても、構図と文字量が凡庸なら「デザインされた資料」ではない。承認済み資料から抽出したDNAを、ページの役割ごとに適用する。

## 目視レビュー用の出力形式

機械的な合否ではなく、次の形式で返す。

```text
AI DESIGN REVIEW

総評: 10〜20点相当 / 要全面改稿
結論: 見た目の整頓はあるが、デザインとしての主役・変化・意味が弱い

最重要の問題 3つ:
1. ...
2. ...
3. ...

ページ別レビュー:
- Slide 01: Critical / ...
- Slide 02: Major / ...

直す順番:
1. カスタマージャーニーとページの役割を再設計
2. 構図を目的別に作り直す
3. ビジュアルを主張に合わせて選び直す
4. 文字量と折返しを整える
5. 再レンダリングして全ページを再レビュー
```

評価は文章が主で、点数は判断を補助するだけにする。80点以上でも、デッキ全体がAIテンプレートに見えるなら合格にしない。

## 実行に使う道具

道具は画像を作るためだけに使う。品質を判定するのはAIの目視レビューである。

1. PowerPointまたはPDFを16:9のPNGへレンダリングする。
2. コンタクトシートでデッキの流れを見る。
3. `view_image` などで全ページを個別に原寸確認する。
4. 目視レビュー記録を `.txt` または `.md` に残す。
5. 修正して再レンダリングし、全ページを再確認する。

`slides_test.py`、独自のフォントサイズチェッカー、座標スコア、要素数スコアは、このスキルの品質判定には使わない。はみ出しや破損の検出を補助的に行う場合も、それをデザイン品質の合否とは混同しない。

## 参照した公開スキルとノウハウ

- [Anthropic PPTX skill](https://github.com/anthropics/skills/tree/main/skills/pptx)：全ページを画像化し、問題がある前提で原寸のVisual QAを行う。問題がなければ「もっと厳しく見る」というレビュー姿勢を採用。
- [Anthropic PPTX editing guide](https://github.com/anthropics/skills/blob/main/skills/pptx/editing.md)：同じレイアウトを繰り返さず、内容の種類に応じて画像、引用、比較、統計、セクションなどを使い分ける。
- [opitaru-sys/deck-dna](https://github.com/opitaru-sys/deck-dna)：承認済み資料からDesign DNAと文字量の上限を抽出し、レンダリング後に敵対的なシニアデザイナーレビューを行う。
- [siril9/presentation-skill](https://github.com/siril9/presentation-skill)：自動チェックを通っても資料は悪くなり得るとし、レンダリング画像の目視レビューを必須化する。

これらの文章・コードを転載するのではなく、AI顧問室の資料を改善するためのレビュー手順として再構成する。
